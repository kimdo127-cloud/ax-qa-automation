# 4회차 과제 · 화면 QA 자동화 (피그마 기준 IA → 테스트 → 결함 → 재확인)

> 업무: 기획자의 화면 QA · 선택안: 2안 상용 시스템 + 자동화(구글 시트 + Apps Script + Gemini, 실행은 GitHub Actions) · 예제 자료는 모두 가상

---

## ① 현재 업무 분석

### 발표 문장
저는 **기획자**가 **퍼블리싱(HTML) 화면이 나온 시점**부터 **모든 결함이 실제로 해결된 것을 확인할 때**까지 수행하는 **화면 QA**를 선택했습니다. 현재 **피그마·HTML 화면·데브옵스·엑셀**을 쓰며 **결함을 엑셀에 다시 옮겨 적고, 개발자가 '해결'로 바꾼 건을 하나씩 다시 확인하는 불편**이 있습니다. 이번에는 **IA 작성 → 테스트 → 결함 기록 → 재확인**까지를 개선하고 싶습니다.

### As-Is 흐름
| 단계 | 담당 | 하는 일 | 문서·데이터 |
| --- | --- | --- | --- |
| 1 | 기획자 | 피그마와 HTML을 눈으로 비교하며 화면을 눌러 봄 | 피그마, HTML |
| 2 | 기획자·디자이너 | 문제를 데브옵스에 결함으로 등록 | 데브옵스 작업 항목 |
| 3 | 기획자 | 등록한 ID·내용을 엑셀에 다시 옮겨 적어 관리 | QA 관리 엑셀 |
| 4 | 개발자 | 수정 후 상태를 '해결'로 변경 | 데브옵스 상태값 |
| 5 | 기획자 | '해결' 건을 다시 눌러 보고 엑셀에 결과 표기 | QA 관리 엑셀 |
| 6 | 기획자 | 2차·3차 QA마다 1~5 반복 | 차수별 엑셀 |

### 문제
1. **확인 범위가 사람 기억에 의존**: 화면·영역·버튼 단위 목록(IA)이 없어 차수마다 빠지는 곳이 생김
2. **이중 기록**: 데브옵스에 올린 내용을 엑셀에 다시 옮겨 적음
3. **'해결' 표시와 실제 해결이 다름**: 개발자가 해결로 바꿔도 실제로는 안 된 건이 있어 전부 다시 확인해야 함
4. **차수별 이력이 흩어짐**: 몇 차에 발견·재오픈·종료됐는지 한눈에 안 보임

### 근거 사례 (조사)
- 키다리스튜디오: 기획서·피그마·화면 → Claude가 테스트케이스 작성 → 사람 승인. 1페이지 3~4시간 → 2~5분, 초안 커버리지 70~80% ([AWS 블로그](https://aws.amazon.com/ko/blogs/tech/amazon-bedrock-langgraph-qa-automation/))
- 엑셈 LLM플랫폼팀: Claude Code + Playwright로 실제 브라우저 테스트, 실패 시 이슈 자동 등록. AI가 테스트를 고쳐 통과시키는 문제가 있어 원인 판정 규칙을 둠 ([엑셈 블로그](https://ex-em.com/ko/blog/2beddf18253e80dcba20f23ce6af5daa))
- 표준 흐름(ISTQB): 근거 문서 → 테스트 시나리오 → 테스트케이스 → 수행 → 결함, ID로 추적
- Azure DevOps 표준: Resolved = 수정했지만 미검증, 테스터가 확인 후 Closed(Verified), 실패 시 Active(Not Fixed)

## ② 개선 설계

### To-Be 흐름
```
[기획자] 피그마 링크 · 테스트 URL · 기획 메모 입력 (구글 시트 'QA 실행' 창)
   ↓
[AI · Gemini] IA(화면>영역>요소) → 테스트 시나리오 → 테스트케이스(실행 단계 포함) 작성
   ↓
[기획자] 시트에서 IA·테스트케이스 검토
   ↓  'QA 실행' 버튼
[시스템 · GitHub Actions + Playwright] 실제 브라우저로 테스트케이스 수행, 실패 화면 캡처
   ↓
[시스템 · Apps Script] N차 결과 열 추가, 실패는 결함 시트에 등록(재현 절차·기대/실제·스크린샷·심각도)
   ↓
[개발자] 결함 시트 '개발자 표기'에 수정완료
   ↓  다음 차수 'QA 실행'
[시스템] 다시 수행 → 통과면 '재확인 통과·종료', 실패면 '재오픈'
   ↓
[기획자] 재오픈·확인 필요 건 최종 판정, 요약 시트로 차수별 현황 확인
```

### 역할 구분
| 구분 | 하는 일 |
| --- | --- |
| AI(Gemini) | IA·시나리오·테스트케이스 초안 작성 (기대 결과는 피그마·기획 메모 기준) |
| 시스템 | 브라우저 실행, 결과·결함·스크린샷 기록, 재확인 후 종료/재오픈, 요약 |
| 기획자 | 입력, 테스트케이스 검토, 결함 최종 판정 |
| 개발자 | 수정 후 '수정완료' 표기 (종료는 시스템 재확인 뒤에만) |

### 구글 시트 구성 (추적: IA ID ↔ 시나리오 ↔ TC ↔ 결함)
입력 · IA · 테스트 시나리오 · 테스트케이스(차수별 결과 열) · 결함 · 실행 기록 · 요약

### 선택 이유
- 실무자는 **구글 시트만 열고 버튼**을 누르면 됨 (기존 엑셀 관리 방식과 같은 화면)
- Apps Script만으로는 브라우저 클릭 테스트가 불가 → **GitHub Actions(무료)에서 Playwright 실행**
- 버튼 동작 확인이 핵심이라 HTML 코드만 읽는 방식은 제외

### 비용·운영
- Gemini API 무료 등급(경량 모델 gemini-3.5-flash-lite), GitHub Actions 비공개 저장소 무료 시간, 구글 시트 무료
- 키 3개(Gemini, GitHub, 피그마)는 시트의 스크립트 속성에만 저장, 제출물에 없음

## ③ 구현물과 실행 방법

**시연 결과(예제)**: 1차 QA 11건 중 실패 5 → 결함 5건 자동 등록(스크린샷 포함). 개발자가 5건 모두 '수정완료' 표기(실제 수정 3건) → 2차 QA에서 실제로 고친 건은 재확인 통과·종료, 오류 문구 2건은 재오픈.

- 구글 시트: 4회차_QA자동화 (메뉴 'QA 자동화')
- 저장소: `ax-qa-automation` (apps-script/ · runner/ · .github/workflows/qa.yml · example-site/ · design/)
- 예제: 피그마 디자인 4화면 / 오류 5개를 심은 테스트 대상 사이트

**실행 방법**
1. 시트 메뉴 QA 자동화 → 설정: Gemini·GitHub·피그마 키 입력 (최초 1회)
2. QA 실행 창 → 피그마 링크·테스트 URL·기획 메모 입력 → 'IA · 시나리오 · 테스트케이스 만들기'
3. 'QA 실행' → 1~3분 뒤 테스트케이스·결함·요약 시트 확인
4. 결함 시트 '개발자 표기'에 수정완료 → 다시 'QA 실행' → 재확인 통과/재오픈 확인

**작동한 기능 / 남은 문제**
| 작동 | 남은 문제 |
| --- | --- |
| 피그마·HTML·기획 메모 → IA·시나리오·테스트케이스 생성 | AI가 만든 테스트 단계가 틀려 '실패'로 잡히는 경우 있음 → 기획자 판정 필요 |
| 실제 브라우저 실행, 결함·스크린샷 자동 기록 | 간격·정렬 같은 시각 차이는 아직 미비교 (문구·색·동작만) |
| 수정완료 건 재확인 → 종료/재오픈, 차수별 이력 보존 | 데브옵스 연동 없음 (계정 생기면 결함 등록·상태 동기화 연결) |
| | AI 테스트케이스가 화면 제목 오타(예제의 '수강 산청')를 확인 항목에서 빠뜨림 → IA 기준 누락 점검 필요 |
| | 2차에서 TC-11은 수정됐지만 테스트 단계(신청 없이 완료 화면 진입) 문제로 재오픈 → 테스트 오류와 실제 결함 구분 필요 |
